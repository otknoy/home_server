# Talos / Kubernetes の更新

このリポジトリの `k8s/talos/Makefile` が管理するバージョンを対象にする。Renovate の設定追加は行わない。日本語で簡潔に報告する。

## 現状と候補の確認

リポジトリの指示、作業差分、`k8s/talos/Makefile`、`k8s/talos/README.md`、関連パッチを読む。既存のユーザー変更を保持する。

`TALOS_VERSION`、`KUBERNETES_VERSION`、`TALOS_IMAGE`、`TALOS_SCHEMATIC_ID` を確認する。値をこのスキルに固定しない。Makefile の値と実クラスタの稼働バージョンは区別する。

指定バージョンがあれば候補に含め、指定がなければ公式の安定版から互換性と更新経路を満たす候補を調べる。最新版という理由だけで両方を引き上げない。

## 互換性と更新経路

実行時に以下の公式情報を検索・閲覧し、参照 URL と確認結果を残す。過去の知識やタグ一覧だけで互換性を判断しない。

- [Talos 公式ドキュメント](https://docs.siderolabs.com/talos/)の対象バージョンの support matrix、Talos / Kubernetes のアップグレード手順と変更点。旧版は [talos.dev](https://www.talos.dev/) も参照する。
- [Talos リリース](https://github.com/siderolabs/talos/releases)と [Kubernetes リリース](https://github.com/kubernetes/kubernetes/releases)の公開状況、既知の問題、破壊的変更。
- [Kubernetes version skew policy](https://kubernetes.io/releases/version-skew-policy/)と必要な中間更新。

最終状態だけでなく各更新段階の Talos / Kubernetes の組み合わせがサポートされることを確認し、更新順序を決める。OS と Kubernetes の更新順序を決め打ちしない。

必要に応じて talosctl / kubectl の条件、schematic の拡張機能と対象 Talos の互換性、既存ワークロードが使う API の廃止・変更を確認する。schematic やインストーラー形式を無断で置き換えない。

情報不足や非対応の組み合わせは報告し、互換性を確認できない値に変更しない。実機情報が必要なら読み取りコマンドを使うかユーザーに確認する。接続できなければ実機確認を未実施と明記する。

## 更新候補の提示とユーザーの選択

ファイルを編集する前に、調査した更新候補を表で提示する。各候補について、更新後の Talos / Kubernetes の組み合わせ、現状からの変更、互換性の根拠、必要な中間更新と順序、主な注意点・未確認事項を示す。パッチ更新とマイナー更新など、実際に選択可能な候補を比較し、推奨候補には理由を添える。候補が一つだけならその旨を伝える。更新見送りも選べるようにする。

ユーザーに候補を選択してもらい、回答を待つ。回答前に Makefile の編集、設定生成、実クラスタの変更を行わない。推奨候補や無回答を選択済みと扱わない。既に具体的な更新先が明示的に選択されている場合は、その候補の調査結果を提示し、同じ選択を繰り返し求めない。選択された候補が非対応なら変更せず、理由と代替候補を提示する。

## 編集と検証

調査のみ、または更新見送りが選択された場合は編集しない。更新依頼ではユーザーが選択した候補に従って、根拠を確認できた変数だけを変更し、Talos の v 付き表記と Kubernetes の v なし表記を維持する。ネットワーク、ストレージ、生成済み設定、シークレットは変更対象に含めない。

- `make -n -C k8s/talos upgrade` と `make -n -C k8s/talos upgrade-k8s` でイメージと更新先の展開を確認する。これは実機検証ではない。
- `git diff --check` と対象差分を確認する。YAML を変更する場合はリポジトリの整形・検証指示に従う。
- `make generate` は secrets を使い、`--force` で設定を生成する。`make validate` も generate を実行してノードに接続する。ローカル構文確認として実行せず、生成・接続が依頼範囲に含まれる場合だけ入力、出力先、認証先を確認して実行する。参照するパッチや secrets の不足は報告し、無関係な修正を混ぜない。

## 実クラスタの更新

Makefile の更新依頼だけではクラスタ変更の許可と解釈しない。実クラスタの更新が明示的に依頼されていれば許可範囲で進め、同じ承認を繰り返し求めない。

実行前に稼働バージョン、接続先、ノード構成、health、etcd バックアップと復旧方法を確認し、実機状態から経路を再評価する。単一ノードなら再起動による停止時間を説明する。準備不足は変更前に解消する。

経路を一段階ずつ進め、各段階で health と実際のバージョンを確認する。複数ノードでは Makefile の NODE だけで全ノードを更新できると仮定しない。health の失敗や想定外の状態があれば次段階へ進まず、状態と復旧方針を報告する。無条件の再試行やダウングレードは行わない。

## 報告

変更前後のバージョン、根拠となる公式 URL、中間更新と順序、実施した検証、未確認事項を簡潔に示す。Makefile の編集完了と実クラスタの更新完了を区別する。
